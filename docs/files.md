# Uploads (`files` profile)

The boson files service ([boson-chat/files](https://github.com/boson-chat/files))
lets people upload files (images, video, audio, documents) that the boson
app links in chat. Each person gets a quota over a rolling window, files
expire on their own, and guests (no account) can upload with smaller
limits. It's optional and **off by default**: add `files` to
`COMPOSE_PROFILES`, then switch uploads on in `config/boson.yaml` (or the
admin panel's **Uploads** page).

| Service | Profile | What it does |
|---|---|---|
| `files` | `files` | public API and downloads on `:8080`, routed by Traefik at `https://FILES_HOST`; internal API on `:3001` (compose network only, never routed) |
| `files-data-init` | `files` | makes the `files_data` volume writable for uid 65532, then exits |
| `minio` | `minio` | optional S3-compatible store for the files (internal only) |
| `minio-init` | `minio` | creates the bucket and a bucket-only user for `files`, then exits |

It needs the `auth` profile: accounts sign in with the stack's auth tokens
(checked against its JWKS, like the directory), and its data lives in its
own database in the stack Postgres.

## Hostname and DNS

`FILES_HOST` (default `files.$DOMAIN`) serves the uploaded files, so it
**must be its own hostname**, never the app's, auth's or the admin panel's
origin: a file someone uploaded must never run with another site's cookies
or origin. The service also sends `Content-Security-Policy: sandbox`,
`X-Content-Type-Options: nosniff`, and `Content-Disposition: attachment` for
everything but a short list of safe types (svg and html are always
downloads).

1. Add an A/AAAA record for `FILES_HOST` pointing at this server.
2. Add `FILES_HOST` to `CERT_HOSTS` so Traefik gets its certificate
   (`scripts/setup.sh` does both when you pick the `files` profile).

## Turning it on

1. `.env`: `files` in `COMPOSE_PROFILES` (with `auth`), `FILES_HOST`,
   `CERT_HOSTS`, and the secrets below (`scripts/setup.sh` generates them).
2. Existing install: create the database (below).
3. `docker compose up -d` (this also recreates `auth` and `admin`, which
   get `FILES_PUBLIC_URL` / the internal token).
4. Switch it on: in the admin panel's **Uploads** page, or by hand:

   ```yaml
   files:
     enabled: true
   ```

5. Check: `https://FILES_HOST/v1/config` says `"enabled": true`, and auth's
   `https://AUTH_HOST/v1/config` has `"files_url": "https://FILES_HOST"`.

## Settings (`.env`)

| Variable | Default | |
|---|---|---|
| `FILES_HOST` | `files.$DOMAIN` | public hostname (own host; add to `CERT_HOSTS`) |
| `FILES_IMAGE` | `harbor.floret.dev/boson/files:1.0.1` | |
| `FILES_ENABLED` | `false` | default only: `config/boson.yaml` `files.enabled` wins. Read by `files` and `auth` |
| `FILES_DB_PASSWORD` | – | generated by `scripts/setup.sh` |
| `FILES_DB_NAME`, `FILES_DB_USER` | `files` | |
| `FILES_INTERNAL_TOKEN` | – | `X-Internal-Token` for the internal API (`:3001`); the admin panel sends it. `openssl rand -hex 32` |
| `FILES_GUEST_SECRET` | – | signs guest tokens (HMAC), 16+ characters; empty = guests off. `openssl rand -hex 32` |
| `FILES_GUEST_TOKENS_PER_HOUR` | `10` | guest tokens one IP may get per hour |
| `FILES_UPLOAD_TIMEOUT` | `30m` | how long one upload may take to send its body |
| `TRAEFIK_READ_TIMEOUT` | `35m` | Traefik's read timeout on `:443` (see [Upload timeouts](#upload-timeouts)) |
| `TRAEFIK_IDLE_TIMEOUT` | `180s` | idle keep-alive connections on `:443` |
| `FILES_S3_ACCESS_KEY`, `FILES_S3_SECRET_KEY` | – | S3 keys for `storage.driver: s3`. Secrets: only in `.env`, never in the config file |
| `FILES_LOG_LEVEL` | `info` | |
| `ADMIN_FILES_INTERNAL_URL` | `http://files:3001` | where the admin panel reaches the internal API; empty without the profile |
| `MINIO_ROOT_USER`, `MINIO_ROOT_PASSWORD` | – | `minio` profile root credentials (generated) |
| `FILES_S3_BUCKET` | `boson-files` | the bucket MinIO creates (`MINIO_DEFAULT_BUCKETS`) |
| `MINIO_MEM_LIMIT` | `320m` | MinIO's memory cap |
| `MINIO_BROWSER` | `off` | MinIO's web console (port 9001, never published) |

What compose passes to `files`: `FILES_PUBLIC_URL=https://FILES_HOST`,
`INTERNAL_TOKEN`, `FILES_GUEST_SECRET`, `BOSON_CONFIG=/config/boson.yaml`,
`AUTH_ISSUER` and `AUTH_JWKS_URL=http://auth:8080/.well-known/jwks.json`
(the default, `$AUTH_ISSUER/.well-known/jwks.json`, is the public host,
which doesn't resolve inside the compose network), `DATABASE_URL`,
`FILES_DATA_DIR=/data`, the S3 keys, `TRUSTED_PROXIES` (Traefik's subnet,
for client IPs and per-IP guest limits), `FILES_GUEST_TOKENS_PER_HOUR` and
`FILES_UPLOAD_TIMEOUT`. The image is distroless (uid 65532, no shell), so
compose has no healthcheck for it; `/healthz` and `/readyz` are on `:3001`.

### Upload timeouts

Traefik v3 closes a request that hasn't been read completely within 60 s by
default, which would cut off large or slow uploads. The stack raises the
`websecure` entrypoint's read timeout to `TRAEFIK_READ_TIMEOUT` (35 min,
longer than `FILES_UPLOAD_TIMEOUT`). There is only one `:443` entrypoint,
so this applies to every router on it; idle keep-alive connections still
close after `TRAEFIK_IDLE_TIMEOUT` (180 s), and each service keeps its own
timeouts. There's no body-size limit in Traefik: `files` enforces
`max_file` and the quota itself (before reading the body, from
`Content-Length`).

## Settings (`config/boson.yaml` `files:`)

Hot-reloaded like the other sections; the admin panel's **Uploads** page
writes them (`settings.manage`). Everything applies live except
`storage.driver` and `storage.s3.*`, which need a restart of `files` (its
config status lists them under `restart_required`, and the panel offers
the restart).

Sizes are a byte count or a number with a unit: `KB`/`MB`/`GB`/`TB` are
**decimal** (1GB = 1000MB = 1,000,000,000 bytes), `KiB`/`MiB`/`GiB`/`TiB`
are binary (1GiB = 1024MiB). Durations are Go durations (`72h`, `30m`).

| Key | Default | |
|---|---|---|
| `files.enabled` | `FILES_ENABLED` (`false`) | the switch. auth publishes `files_url` only while it's on |
| `files.retention` | `72h` | a file is deleted this long after its upload |
| `files.window` | `72h` | the rolling quota window |
| `files.account.quota` / `max_file` | `5GB` / `100MB` | per account per window / per file |
| `files.guest.enabled` | `true` | guests may upload |
| `files.guest.quota` / `max_file` | `500MB` / `25MB` | per guest token per window / per file |
| `files.storage.driver` | `local` | `local` (the `files_data` volume) or `s3`. **Restart** |
| `files.storage.min_free` | `2GB` | refuse uploads (`507 storage_full`) that would leave less free |
| `files.storage.capacity` | – | s3 only: total budget for the bucket (S3 has no free-space API); without it s3 has no guard |
| `files.storage.s3.endpoint`, `bucket`, `region`, `path_style`, `public_base_url` | –, –, `auto`, `true`, – | S3 settings; keys come from `.env`. **Restart** |

The full commented reference is in `config/boson.example.yaml`.

## Quota

- What counts is everything a person uploaded in the last `window`,
  including files they deleted and files that already expired. **Deleting
  doesn't give space back**: the file is removed at once, but its size
  counts until the upload leaves the window.
- An upload over the quota gets `413 quota_exceeded` with `frees_at` (when
  enough old uploads leave the window for it); a file over `max_file` gets
  `413 file_too_large`; when the server is out of space, `507 storage_full`
  (see [Disk space](#disk-space)). `GET /v1/me/usage` lists when space comes back, for
  the app's "1.2 GB of 5 GB, 1 GB frees in 20 h".
- Files are deleted from storage at upload + `retention` (the expiry worker
  runs every minute); downloads then answer `410` with a small "this file
  has expired" page (`404` for ids that never existed).
- Guests get a short-lived token from `POST /v1/guest-token` (24 h,
  rate-limited per IP) and send it as `Authorization: Guest <token>`. Their
  limits apply per token and per IP (the IP gets 3x the guest quota, so new
  tokens don't reset it). `files.guest.enabled: false` turns guest uploads
  off.

## Storage

- **`local`** (default): files in the `files_data` volume. Back it up with
  `pg_data`, or treat uploads as disposable (they expire anyway).
- **`s3`**: any S3-compatible store. By default downloads still go through
  `https://FILES_HOST/f/…`, so the safe headers always apply; set
  `public_base_url` only to serve straight from a public bucket or CDN.
  - **Cloudflare R2**: `endpoint: https://<account id>.r2.cloudflarestorage.com`,
    `region: auto`, `path_style: true`, an R2 API token with Object
    Read & Write on that bucket as `FILES_S3_ACCESS_KEY` / `FILES_S3_SECRET_KEY`.
  - **AWS S3**: `endpoint: https://s3.<region>.amazonaws.com`, the region,
    `path_style: false`.
  - **MinIO on this host**: the `minio` profile below.

### `minio` profile

```sh
COMPOSE_PROFILES=...,auth,files,minio
```

```yaml
files:
  storage:
    driver: s3
    capacity: 15GB
    s3: { endpoint: "http://minio:9000", bucket: boson-files, region: auto, path_style: true }
```

Then `docker compose up -d` and `docker compose restart files` (the driver
needs a restart).

- **Image**: upstream MinIO stopped publishing container images, so the
  stack pins Bitnami's last builds, `bitnamilegacy/minio:2025.7.23-debian-12-r5`
  and `bitnamilegacy/minio-client:2025.7.21-debian-12-r3` (for
  `minio-init`). They no longer get updates: keep MinIO internal (as here).
  Change the tags in `compose.yaml` to move to another build.
- **Bucket**: MinIO creates `FILES_S3_BUCKET` (default `boson-files`) at
  start (`MINIO_DEFAULT_BUCKETS`); `minio-init` also makes sure it exists.
- **Internal only**: the S3 API (`:9000`) is neither published on the host
  nor routed by Traefik, and the web console is off (`MINIO_BROWSER=off`).
  To use the console: set `MINIO_BROWSER=on`, `docker compose up -d minio`,
  then tunnel to it, `ssh -L 9001:<minio container IP>:9001 <host>` (the IP
  from `docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' boson-minio-1`),
  open `http://localhost:9001` and sign in with the root credentials. Turn
  it off again afterwards.
- **Credentials**: `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` (generated by
  `scripts/setup.sh`) are only used by `minio-init`. MinIO refuses to start
  without them (the image would otherwise fall back to `minio` /
  `miniosecret`).
- **`minio-init`** runs on every `up` (idempotent) and exits: it creates the
  policy `boson-files` (`s3:ListBucket` and `s3:GetBucketLocation` on
  `arn:aws:s3:::<bucket>`; `s3:GetObject`, `s3:PutObject` and
  `s3:DeleteObject` on `arn:aws:s3:::<bucket>/*`), the user
  `FILES_S3_ACCESS_KEY` / `FILES_S3_SECRET_KEY` (a changed secret is
  applied) and attaches the policy. `files` uses that user, never the root
  credentials: it can't create buckets, read other buckets or administer
  MinIO. The same by hand, if you ever need it:

  ```sh
  docker compose run --rm --entrypoint sh minio-init -c '
    mc alias set local http://minio:9000 "$MINIO_ROOT_USER" "$MINIO_ROOT_PASSWORD"
    mc admin user add local "$FILES_S3_ACCESS_KEY" "$FILES_S3_SECRET_KEY"
    mc admin policy attach local boson-files --user "$FILES_S3_ACCESS_KEY"'
  ```
- **Healthcheck**: `curl http://127.0.0.1:9000/minio/health/live`;
  `minio-init` waits for it.
- **Memory**: `mem_limit: 320m` (`MINIO_MEM_LIMIT`), sized for a 2 GB VPS.
- **Data**: the `minio_data` volume (`/bitnami/minio/data`). Back it up if
  uploads matter to you.

### Disk space

With `local` or `minio`, the host's disk bounds total storage: on a VPS
with ~24 GB free, quota × active uploaders over a window can exceed it
(5 GB × 5 people is already 25 GB). The storage guard keeps uploads from
filling the disk: an upload that would leave less than
`files.storage.min_free` (default `2GB`) free is refused with
`507 storage_full` ("server storage is full, try again later" in the app).

- **local**: the guard checks the `files_data` volume's free space.
- **s3** (MinIO, R2, AWS): S3 has no free-space API, so set
  `files.storage.capacity` to a total budget; the guard checks it against
  what files keeps in the bucket. For MinIO on the same ~24 GB disk,
  `capacity: 15GB` leaves room for Postgres, images and logs. Without
  `capacity`, s3 has no guard.

The admin panel's Uploads page shows free, used and total space and whether
the guard is refusing uploads.

## Discovery

- `https://DOMAIN/.well-known/boson.json` (`wellknown` profile) gets
  `"files": {"url": "https://FILES_HOST"}` whenever `files` is in
  `COMPOSE_PROFILES` (or `WELLKNOWN_SECTIONS`).
- auth's `GET /v1/config` has `files_url`: `https://FILES_HOST` while
  uploads are on (`files.enabled`, default `FILES_ENABLED`), otherwise
  `null`. Apps hide the attach button when it's `null`.

## Admin panel

With `BOSON_FILES_INTERNAL_URL` (`ADMIN_FILES_INTERNAL_URL`, default
`http://files:3001`) and `BOSON_FILES_INTERNAL_TOKEN` (`FILES_INTERNAL_TOKEN`):

- **Uploads** (`settings.manage`): the switch, retention and window,
  account and guest limits, storage driver and S3 settings (the keys stay
  in `.env`), and the service's live status (storage health, totals).
  Saved to `config/boson.yaml` and logged with who saved.
- **Uploaded files** (`users.moderate`): list and search files, open,
  delete (logged with the moderator). A user's page shows their usage.

The panel also asks `http://files:3001/internal/config/status` whether
`files` applied the last save (`ADMIN_CONFIG_STATUS_TARGETS`).

## Existing installs

`postgres/initdb/30-files.sh` only runs when the Postgres volume is
created. On an install that already has data, create the database once:

```sh
P=$(grep ^FILES_DB_PASSWORD= .env | cut -d= -f2-)
docker compose exec -T postgres psql -U auth -d postgres \
  -v pw="$P" -v usr=files -v db=files <<'SQL'
CREATE ROLE :"usr" LOGIN PASSWORD :'pw';
CREATE DATABASE :"db" OWNER :"usr";
SQL
```

Add the new secrets to `.env` (`FILES_DB_PASSWORD`, `FILES_INTERNAL_TOKEN`,
`FILES_GUEST_SECRET`, and for `minio` `MINIO_ROOT_USER`,
`MINIO_ROOT_PASSWORD`, `FILES_S3_ACCESS_KEY`, `FILES_S3_SECRET_KEY`):

```sh
for v in FILES_INTERNAL_TOKEN FILES_GUEST_SECRET; do echo "$v=$(openssl rand -hex 32)"; done >> .env
echo "FILES_DB_PASSWORD=$(openssl rand -hex 20)" >> .env
```
